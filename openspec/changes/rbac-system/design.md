## Context

构建一个企业级 RBAC 权限管理系统，需要支持多用户、多角色、多菜单的复杂权限管理。系统需要前后端分离架构，前端使用 Vue3 + Element Plus，后端使用 Spring Boot 3.5.16。

当前状态：项目从零开始，需要完整搭建前后端工程。

约束条件：
- 使用 Spring Boot 3.5.16 作为后端框架
- 使用 Vue3 + Element Plus 作为前端框架
- 数据库使用 MySQL，缓存使用 Redis
- 需要支持动态路由和按钮级权限控制

## Goals / Non-Goals

**Goals:**
- 实现完整的用户认证功能（登录、登出、注册）
- 实现用户、角色、菜单的 CRUD 管理
- 实现基于角色的菜单权限分配
- 实现动态路由，根据用户权限生成前端路由
- 实现按钮级权限控制
- 提供清晰的项目结构和代码组织

**Non-Goals:**
- 不实现多租户功能
- 不实现分布式架构
- 不实现工作流引擎
- 不实现数据字典管理
- 不实现日志审计功能

## Decisions

### 1. 认证方案：JWT + Redis

**选择**: 使用 JWT 令牌 + Redis 存储的组合方案

**理由**:
- JWT 无状态，易于扩展
- Redis 存储支持 token 主动失效（登出功能）
- 可以控制单点登录

**替代方案**:
- 纯 JWT：无法主动使 token 失效，不支持登出功能
- Session + Redis：需要服务端存储会话状态，扩展性较差

### 2. ORM 框架：MyBatis Plus

**选择**: 使用 MyBatis Plus 作为 ORM 框架

**理由**:
- 内置 CRUD 操作，减少重复代码
- 支持分页插件
- 支持 Lambda 查询，代码更清晰
- 与 Spring Boot 3.x 兼容性好

**替代方案**:
- JPA/Hibernate：学习曲线较陡，复杂查询不够灵活
- 原生 MyBatis：需要手写大量 SQL，开发效率低

### 3. 前端路由：动态路由

**选择**: 使用动态路由，根据用户权限动态生成前端路由

**理由**:
- 安全性高，用户只能看到有权限的菜单
- 用户体验好，菜单根据权限自动调整
- 支持按钮级权限控制

**替代方案**:
- 静态路由 + 前端控制：前端代码暴露所有路由，安全性较低

### 4. 权限控制：v-permission 指令

**选择**: 使用自定义指令 v-permission 实现按钮级权限控制

**理由**:
- 使用简单，直接在模板中使用
- 权限标识清晰，易于维护
- 可以自动移除无权限的元素

**替代方案**:
- 路由 meta 配置：只能控制页面级权限，无法控制按钮级
- 函数式方式：需要在每个按钮处手动判断，代码冗余

## Risks / Trade-offs

### 风险
1. **Redis 依赖**: 系统依赖 Redis 存储 token，Redis 不可用将导致登录功能失效
   - 缓解：Redis 集群部署，或者降级为纯 JWT 方案

2. **密码安全**: 初始密码为 123456，生产环境需要强制修改
   - 缓解：登录后检查是否使用初始密码，强制修改

3. **并发冲突**: 多人同时编辑同一数据可能导致冲突
   - 缓解：使用乐观锁或版本号机制（当前未实现）

### 权衡
1. **功能完整性 vs 开发效率**: 选择实现核心功能，忽略非核心功能（如日志审计）
2. **安全性 vs 易用性**: JWT token 有效期 24 小时，平衡安全性和用户体验
3. **代码规范 vs 开发速度**: 遵循 Spring Boot 最佳实践，但简化部分配置

## Migration Plan

1. 执行数据库初始化脚本（schema.sql、data.sql）
2. 启动 Redis 服务
3. 启动 Spring Boot 后端服务
4. 启动 Vue3 前端服务

### 回滚策略
1. 停止前后端服务
2. 恢复数据库备份（如有）
3. 重新部署旧版本代码
