类加载器是Java实现“一次编写，到处运行”与动态扩展能力的基石。它的核心作用是**在运行时将`.class`字节码文件加载到JVM内存中，并生成对应的`java.lang.Class`对象**。没有类加载器，JVM就无法执行任何Java代码。

### 🧭 核心作用：不止于“加载”

类加载器的作用贯穿了类生命周期的起始阶段，并延伸出几个关键能力：

1. **动态加载**：Java的类并非在编译期全部载入，而是在**首次主动使用时**才由类加载器动态加载。这使得程序可以按需加载，甚至从网络、数据库等非常规来源获取字节码，是实现**热部署**和**插件化架构**的基础。
2. **类隔离**：不同的类加载器可以加载同一个类（全限定名完全相同）的**不同版本**。在JVM中，**类的唯一性由“类加载器 + 全限定类名”共同决定**。这一特性被Web容器（如Tomcat）广泛用于隔离不同Web应用，防止库版本冲突。
3. **安全与保护**：类加载器体系（特别是双亲委派模型）构成了一道安全防线。例如，它能防止用户自定义一个`java.lang.String`类来替换核心库中的`String`，避免恶意代码篡改基础行为。

### 🗂️ 分类：内置加载器与JDK 9+的变化

Java的类加载器体系在JDK 9模块化系统（JPMS）引入后发生了重要变化，但层次结构得以保留。

| 加载器类型 | **JDK 8及之前** | **JDK 9及之后** | 核心职责 | 父加载器 |
| :--- | :--- | :--- | :--- | :--- |
| **启动类加载器** | Bootstrap ClassLoader | Bootstrap ClassLoader（不变） | 加载Java核心库（如`java.base`模块） | 无（在API中显示为`null`） |
| **平台/扩展类加载器** | Extension ClassLoader | **Platform ClassLoader**（更名） | JDK 8：加载`ext`目录；**JDK 9+：加载Java SE平台中非`java.base`的模块** | 启动类加载器 |
| **系统/应用类加载器** | Application ClassLoader | Application ClassLoader（不变） | 加载**用户类路径（Classpath）** 上的所有类 | 平台类加载器 |
| **自定义类加载器** | 用户继承`ClassLoader` | 用户继承`ClassLoader` | 灵活地从网络、加密文件等来源加载类，或实现隔离 | 通常为系统类加载器 |

**关键变化说明（JDK 9+）**：
* **扩展加载器更名为平台加载器**：原先的“扩展”机制被移除，`Platform ClassLoader`的职责是确保Java SE平台中除`java.base`外的所有类可见。
* **`rt.jar`等JAR包消失**：核心类库不再以JAR文件形式存在，而是存储在模块化的运行时映像中，这影响了`ClassLoader.getSystemResource()`等方法的返回值格式。

### 🔗 双亲委派模型：工作流程与代码

类加载器的层次关系通过**双亲委派模型（Parent Delegation Model）** 来协同工作。

**工作流程**：当一个类加载器收到加载请求时，它**首先不会自己加载**，而是将请求**委派给父加载器**。这个过程层层上报，直到启动类加载器。只有当父加载器无法完成加载（在其搜索范围内找不到类）时，子加载器才会尝试自己加载。

**核心源码**：这一逻辑集中在`java.lang.ClassLoader`的`loadClass`方法中：
```java
// ClassLoader.loadClass 方法的核心逻辑（简化示意）
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查类是否已被当前加载器加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 2. 如果有父加载器，委派给父加载器
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    // 3. 如果没有父加载器，委派给启动类加载器
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器无法加载，忽略异常，准备自己加载
            }
            if (c == null) {
                // 4. 父加载器无法加载时，调用自己的 findClass 方法
                c = findClass(name);
            }
        }
        // ... (链接与返回)
        return c;
    }
}
```

**层次结构的代码验证**：我们可以通过代码直观地看到这个“委派链”。
```java
public class ClassLoaderHierarchy {
    public static void main(String[] args) {
        // 获取当前类（ClassLoaderHierarchy）的加载器，即系统/应用类加载器
        ClassLoader appLoader = ClassLoaderHierarchy.class.getClassLoader();
        System.out.println("应用类加载器: " + appLoader);

        // 获取其父加载器，在JDK 9+中为平台类加载器
        ClassLoader platformLoader = appLoader.getParent();
        System.out.println("平台类加载器: " + platformLoader);

        // 获取平台加载器的父加载器，应为 null，代表启动类加载器
        ClassLoader bootstrapLoader = platformLoader.getParent();
        System.out.println("启动类加载器 (显示为null): " + bootstrapLoader);

        // 验证核心类由启动类加载器加载
        System.out.println("String类的加载器: " + String.class.getClassLoader()); // 输出 null
    }
}
```
**输出示例（JDK 9+）**：
```
应用类加载器: jdk.internal.loader.ClassLoaders$AppClassLoader@...
平台类加载器: jdk.internal.loader.ClassLoaders$PlatformClassLoader@...
启动类加载器 (显示为null): null
String类的加载器: null
```

### 🛠️ 自定义类加载器：两种典型实现

当内置加载器无法满足需求时（如从特定位置加载、实现隔离），可以自定义类加载器。**关键在于理解重写`findClass`与`loadClass`的区别**。

#### 方式一：遵循双亲委派（推荐）
**只重写`findClass`**。这样既实现了自定义的加载逻辑，又保留了双亲委派带来的安全性和一致性。
```java
public class CustomClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // 1. 实现自定义的字节码获取逻辑（例如从特定目录读取）
        byte[] classBytes = loadClassBytesFromCustomLocation(name);
        if (classBytes == null) {
            throw new ClassNotFoundException(name);
        }
        // 2. 调用 defineClass 将字节数组转换为 Class 对象
        return defineClass(name, classBytes, 0, classBytes.length);
    }
    private byte[] loadClassBytesFromCustomLocation(String className) {
        // 具体实现：读取文件、网络下载等
        return null; // 示例占位
    }
}
```

#### 方式二：打破双亲委派（谨慎使用）
**重写`loadClass`方法**，改变“先委派父加载器”的默认逻辑，变为“**先尝试自己加载**”。
```java
public class BrokenDelegationClassLoader extends ClassLoader {
    private final ClassLoader parent;
    public BrokenDelegationClassLoader(ClassLoader parent) {
        this.parent = parent;
    }
    @Override
    public Class<?> loadClass(String name) throws ClassNotFoundException {
        // 1. 首先尝试自己加载
        try {
            return findClass(name);
        } catch (ClassNotFoundException e) {
            // 2. 自己加载失败，再委派给父加载器
            return parent.loadClass(name);
        }
    }
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // ... 自定义加载逻辑
        return defineClass(name, classBytes, 0, classBytes.length);
    }
}
```
> **注意**：这种方式打破了双亲委派的保护，可能引发核心类被篡改或类冲突的风险，通常只在SPI（服务提供者接口）、应用服务器隔离等特定场景下由框架层谨慎使用。
