Java 反序列化失败很少是一个“孤立”的问题，它通常指向**序列化契约**在某一环被破坏了。下面按异常类型与典型场景展开，每个场景尽量给出可复现的代码。

---

## 一、`InvalidClassException`：类兼容性被破坏

`InvalidClassException` 是反序列化失败中最常见的一类，直接原因是**流中记录的类描述与本地加载的类定义不匹配**。

### 1. `serialVersionUID` 不一致

Java 序列化机制依赖 `serialVersionUID` 判定类版本是否兼容。如果序列化时的类与反序列化时的类 `serialVersionUID` 不同，`ObjectInputStream` 会拒绝继续，抛出类似：

```
java.io.InvalidClassException: Person; local class incompatible:
stream classdesc serialVersionUID = 1, local class serialVersionUID = 2
```

如果类没有显式声明 `serialVersionUID`，编译器会根据类结构自动计算一个值。**只要类有任何结构性改动，这个自动值就会改变**，即使你只是加了一个无关紧要的字段或方法。

**失败示例**：序列化后，在类中显式修改 `serialVersionUID`（或删掉显式声明后依赖自动生成）：

```java
class Person implements Serializable {
    // 序列化时是 1L，反序列化时改成了 2L
    private static final long serialVersionUID = 2L;
    private String name;
}
```

反序列化时即抛出 `InvalidClassException`。

**规避方式**：对需要跨版本或跨进程反序列化的类，**始终显式声明 `serialVersionUID`**，并且在不希望拒绝旧数据时不要随意改动它。

### 2. 类结构发生不兼容变更

即使 `serialVersionUID` 保持不变，某些字段级变更仍然是**不兼容的**，会导致反序列化失败或产生错误状态。

**典型不兼容变更包括**：

- **删除字段**：新类无法为旧流中存在的字段找到对应位置，`defaultReadObject` 可能抛出 `InvalidClassException` 或相关异常。
- **修改字段类型**：例如 `int age` 改为 `String age`。流中存储的是 `int` 类型的字节，本地期望 `String`，类型不匹配，反序列化失败。
- **将 `Serializable` 改为 `Externalizable` 或反向变更**：流的组织方式完全不同，彼此无法解析。

**失败示例（字段类型变更）**：

```java
// 旧版本
class User implements Serializable {
    private static final long serialVersionUID = 1L;
    private int age;
}

// 新版本（serialVersionUID 未变，但字段类型变了）
class User implements Serializable {
    private static final long serialVersionUID = 1L;
    private String age;  // 反序列化旧流时失败
}
```

**兼容的变更**（在 `serialVersionUID` 相同的前提下）：**新增字段**通常是兼容的，旧流中没有该字段，反序列化后新字段取默认值（`0` / `false` / `null`）；但**删除字段**和**修改字段类型**通常不兼容。

## 二、构造器不执行引发的“逻辑失败”

`ObjectInputStream` 在反序列化一个 `Serializable` 类时，**不会调用该类的任何构造器，也不会执行实例初始化块和字段初始化器**（`field initializer`）。它只调用**第一个不可序列化的父类的无参构造器**。

这一行为本身不是异常，但会导致一类隐蔽的“反序列化失败”：对象在语法上被成功还原，但业务状态缺失或错误。

### 场景：`transient` 字段在反序列化后为默认值

`transient` 字段不参与序列化，而构造器又不执行，因此没有任何代码会为它重新赋值。

```java
class Session implements Serializable {
    private static final long serialVersionUID = 1L;
    private String userId;
    private transient List<String> permissions = new ArrayList<>(); // 初始化器不会执行

    public Session(String userId) {
        this.userId = userId;
        permissions.add("read");
    }
}
```

序列化并反序列化后，`userId` 被恢复，但 `permissions` 为 `null`，后续调用 `permissions.add(...)` 会抛出 `NullPointerException`，看起来像是“反序列化失败”，实际上是**反序列化跳过了你依赖的初始化逻辑**。

**修复方式**：在类中实现 `private void readObject(ObjectInputStream in)`，先调用 `in.defaultReadObject()`，再手动重建 `transient` 或派生状态：

```java
private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    this.permissions = new ArrayList<>();  // 恢复 transient 字段
    if (userId != null) {
        permissions.add("read");
    }
}
```

## 三、`ClassNotFoundException`：反序列化时找不到类

流中存储了对象的类名，但 `ObjectInputStream` 在当前类路径或当前 `ClassLoader` 中找不到对应的类，抛出 `ClassNotFoundException`。

常见触发方式：

- 序列化了一个**匿名内部类**或**局部类**，其类名形如 `Outer$1`，反序列化时该内部类的字节码不在类路径中。
- 类被重命名或移动到了不同的包。
- 反序列化发生在不同的模块或 `ClassLoader` 上下文中。

**示例**：对一个匿名内部类实例执行序列化后，将类文件移出类路径，再反序列化：

```java
Object obj = new ObjectInputStream(new FileInputStream("inner.ser")).readObject();
```

如果流中记录的类 `Outer$1` 不在类路径中，就会抛出 `ClassNotFoundException`。

## 四、流本身损坏或格式不对：`StreamCorruptedException` / `OptionalDataException`

### `StreamCorruptedException`

当输入流不是合法的 Java 序列化流，或者流在传输/存储过程中被截断、损坏，`ObjectInputStream` 无法识别流头或后续的流控制标记，会抛出 `StreamCorruptedException`。

例如，把一个普通文本文件当作序列化流读取：

```java
ObjectInputStream ois = new ObjectInputStream(new FileInputStream("plain.txt"));
ois.readObject(); // StreamCorruptedException: invalid stream header
```

也可能是写入时用 `ObjectOutputStream`，读取时却试图从非序列化数据中解析，或流被重置后状态不一致。

### `OptionalDataException`

`OptionalDataException` 通常发生在**自定义 `readObject` 时读取顺序与写入顺序不一致**，或者流中预期是对象数据、却遇到了原始数据类型（primitive）的块。

**典型原因**：写入时使用了 `writeInt`、`writeUTF` 等原始类型方法，读取时却先调用 `readObject`，或顺序相反。`ObjectInputStream` 要求**读取顺序必须与写入顺序严格一致**。

**示例**：

```java
// 写入
out.writeInt(42);
out.writeObject("hello");

// 读取（顺序反了）
Object o = in.readObject(); // OptionalDataException: primitive data in stream
int n = in.readInt();
```

`readObject` 在遇到尚未被读走的原始类型数据时会抛出 `OptionalDataException`。

## 五、`Externalizable` 缺少可访问的无参构造器

`Externalizable` 与 `Serializable` 的关键差异在于：反序列化时，`Externalizable` 类**必须有一个 `public` 的无参构造器**，因为 `ObjectInputStream` 会先通过这个构造器创建实例，再调用 `readExternal` 填充状态。

如果缺少 `public` 无参构造器，反序列化直接失败：

```
java.io.InvalidClassException: ...; no valid constructor
```

**错误示例**：

```java
class Config implements Externalizable {
    private String key;

    public Config(String key) { this.key = key; }
    // 没有 public 无参构造器

    @Override public void writeExternal(ObjectOutput out) throws IOException {
        out.writeUTF(key);
    }
    @Override public void readExternal(ObjectInput in) throws IOException {
        key = in.readUTF();
    }
}
```

反序列化 `Config` 的流时会抛出 `InvalidClassException`，提示没有有效的构造器。

**修复**：为 `Externalizable` 类提供一个 `public` 无参构造器（即使方法体为空）。

## 六、安全过滤导致的“主动失败”

从 Java 9 开始，`ObjectInputFilter` 可以对反序列化的类进行白名单/黑名单控制。如果流中的类不在允许范围内，`ObjectInputStream` 会拒绝继续，抛出 `InvalidClassException`（或被过滤器以其他方式阻断）。

**示例**：只允许 `com.myapp.` 下的类：

```java
ObjectInputStream ois = new ObjectInputStream(inputStream);
ois.setObjectInputFilter(info -> {
    if (info.serialClass() != null
            && info.serialClass().getName().startsWith("com.myapp.")) {
        return ObjectInputFilter.Status.ALLOWED;
    }
    return ObjectInputFilter.Status.REJECTED;
});
ois.readObject();
```

如果流中包含 `java.lang.Runtime`、`java.util.HashMap` 等不在允许范围内的类，反序列化会被拒绝，表现为 `InvalidClassException` 或过滤器抛出的拒绝信息。这属于**有意为之的反序列化失败**，是防御不可信数据的重要手段。

## 七、枚举反序列化：不是异常，但状态会“回退”

枚举常量的反序列化不会抛出典型异常，但有一个容易误解的行为：**反序列化返回的是 JVM 中已经存在的那个枚举常量，而不是根据流中数据重建的新对象**。枚举的实例字段**不会被序列化**，反序列化后字段值保持该常量在当前 JVM 中的初始值或当前值。

**示例**：将 `INSTANCE.value` 设为 `10` 后序列化，在另一个进程中反序列化：

```java
enum MyEnum {
    INSTANCE(5);
    private int value;
    MyEnum(int value) { this.value = value; }
    public void setValue(int v) { this.value = v; }
    public int getValue() { return value; }
}
```

在新进程中反序列化后，`getValue()` 返回 `5`，而不是序列化时的 `10`。原因正是枚举序列化只保存常量名，反序列化时通过 `Enum.valueOf` 取得现有常量，字段状态没有随流恢复。如果业务逻辑依赖枚举字段的运行时状态，这就会表现为一种“反序列化后状态不对”的失败。

## 附：兼容性速查与核心实践

| 变更类型 | 是否兼容（`serialVersionUID` 不变时） |
|---|---|
| 新增字段 | 通常兼容，新字段取默认值 |
| 删除字段 | **不兼容** |
| 修改字段类型 | **不兼容** |
| `static` → 非 `static` / `transient` → 非 `transient` | 等价于新增字段，通常兼容 |
| `Serializable` ↔ `Externalizable` | **不兼容** |
| 修改 `serialVersionUID` | **不兼容**（除非你确实想拒绝旧数据） |

实践上，规避反序列化失败的核心原则是：**对需要持久化或跨版本传输的可序列化类，显式声明 `serialVersionUID`；对不兼容变更保持警惕；对 `transient` 字段和构造器初始化逻辑，通过 `readObject` 显式恢复；对不可信输入，使用 `ObjectInputFilter` 让失败变成主动的安全行为，而不是偶然的崩溃。**
