`InputStreamReader` 在 Java I/O 体系中扮演着一个特定且不可替代的角色：它是**字节流与字符流之间的解码桥梁**。它本身不直接操作数据源，而是包裹一个已有的字节输入流，将读入的原始字节按照指定的字符集解码为 Java 的 Unicode 字符。

### 功能定位：为什么需要它

字节流（`InputStream`）以 8 位字节为单位搬运数据，对内容“无感知”；字符流（`Reader`）则以 16 位 `char` 为单位，携带了文本的语义。`InputStreamReader` 位于两者之间，承担“翻译”职责：从底层字节流读取字节，用指定的 `Charset` 将其解码为字符，供上层字符流 API 使用。没有它，处理文本时就需要手动管理字节数组与编码规则，容易出错。

### 构造器：编码选择的三条路径

`InputStreamReader` 提供四个构造器，差别在于如何指定解码所用的字符集。

**1. 使用平台默认字符集**

```java
InputStreamReader(InputStream in)
```

使用 JVM 所在平台的默认字符集（`Charset.defaultCharset()`）。这是最便捷的方式，但可移植性最差——同一份代码在 Windows（常见 GBK）与 Linux（常见 UTF-8）上的行为可能完全不同，因此**不推荐在需要确定行为的场景中使用**。

```java
try (InputStreamReader reader = new InputStreamReader(new FileInputStream("data.txt"))) {
    // 使用平台默认编码解码
}
```

**2. 按字符集名称指定**

```java
InputStreamReader(InputStream in, String charsetName) throws UnsupportedEncodingException
```

传入编码名称（如 `"UTF-8"`、`"GBK"`）。若平台不支持该编码，抛出受检异常 `UnsupportedEncodingException`。适合编码名称来自外部配置且需要显式捕获异常的场景。

**3. 使用 `Charset` 对象**

```java
InputStreamReader(InputStream in, Charset cs)
```

`Charset` 是 `java.nio.charset` 包中的类型，相比字符串名称，它编译期即可校验，且可以通过 `StandardCharsets.UTF_8` 等常量直接引用，**是推荐的方式**。

```java
try (InputStreamReader reader = new InputStreamReader(
        new FileInputStream("data.txt"), StandardCharsets.UTF_8)) {
    // 明确以 UTF-8 解码
}
```

**4. 使用 `CharsetDecoder`（高级）**

```java
InputStreamReader(InputStream in, CharsetDecoder dec)
```

允许传入自定义配置的 `CharsetDecoder`，可以控制解码错误策略（`CodingErrorAction.REPLACE` / `REPORT` / `IGNORE`），适用于对非法字节序列有特殊容错要求的场景。

### 核心 API 的使用方法

#### `int read()`：读取单个字符

返回读取到的字符的 Unicode 码点（0–65535），流结束时返回 `-1`。这是一个**阻塞调用**：如果底层字节流暂无数据，线程会一直等待，直到有字节可读、流关闭或抛出异常。

```java
try (InputStreamReader reader = new InputStreamReader(
        new FileInputStream("demo.txt"), StandardCharsets.UTF_8)) {
    int ch;
    while ((ch = reader.read()) != -1) {
        System.out.print((char) ch);
    }
}
```

#### `int read(char[] cbuf, int off, int len)`：批量读取

将最多 `len` 个字符读入数组 `cbuf` 从 `off` 开始的位置，返回实际读入的字符数，流结束时返回 `-1`。批量读取比逐字符读取效率更高，因为 `InputStreamReader` 内部会预读底层字节以提高解码效率。

```java
char[] buffer = new char[1024];
int len;
while ((len = reader.read(buffer, 0, buffer.length)) != -1) {
    System.out.print(new String(buffer, 0, len));
}
```

#### `String getEncoding()`：查询当前编码

返回此流实际使用的字符编码名称。如果流已关闭，返回 `null`。注意：如果构造时传入的是名称，返回的可能是该编码的历史名称或规范名称，未必与传入字符串完全一致。

```java
try (InputStreamReader reader = new InputStreamReader(
        new FileInputStream("demo.txt"), "UTF-8")) {
    System.out.println(reader.getEncoding()); // 通常输出 UTF-8
}
```

#### `boolean ready()`：非阻塞就绪探测

`ready()` 的语义需要与 `read()` 对照理解：它返回 `true` 表示**下一次 `read()` 不会因为等待数据而阻塞**。这有两种可能：`InputStreamReader` 的内部缓冲区已有解码后的字符，或者底层字节流已有可读字节。返回 `false` 并不意味着流已结束，只表示立即读取可能阻塞。

因此，`ready()` 适合用于**非阻塞轮询**或**避免在无数据时挂起线程**的场景，但**绝不能**用它来判断流是否结束——判断结束的唯一可靠依据是 `read()` 返回 `-1`。

```java
// 非阻塞地检查是否有数据可读（不保证读到，只保证 read 不会立即阻塞）
if (reader.ready()) {
    int ch = reader.read(); // 此时 read 不会因等待数据而阻塞
}
```

#### `void close()`

关闭流并释放系统资源。`InputStreamReader` 会同时关闭其包裹的底层 `InputStream`。使用 try-with-resources 即可自动管理。

### 实践要点

**优先包裹 `BufferedReader`**。Oracle 文档明确建议：为了获得最高效率，应将 `InputStreamReader` 包装在 `BufferedReader` 中。`BufferedReader` 按行读取的能力（`readLine()`）也是逐字符或固定数组读取难以替代的。

```java
try (BufferedReader br = new BufferedReader(
        new InputStreamReader(new FileInputStream("demo.txt"), StandardCharsets.UTF_8))) {
    String line;
    while ((line = br.readLine()) != null) {
        System.out.println(line);
    }
}
```

**编码必须显式指定**。依赖平台默认编码是跨平台问题的常见根源。`StandardCharsets.UTF_8` 是最通用的选择；如果数据源确定使用 GBK 等编码，则必须显式传入对应 `Charset`。

**不要在 `InputStreamReader` 外层再直接操作底层 `InputStream`**。`InputStreamReader` 会预读字节以提高解码效率，如果绕过它直接从底层流读取，预读的字节已被消耗，后续读取将出现不可预期的数据丢失或错位。

**`ready()` 不是 EOF 判断**。在多数实现中，`ready()` 在到达流末尾之前会持续返回 `true`，到达 EOF 后才返回 `false`；但它的契约只保证“不阻塞”，不保证“流未结束”。判断读取终止始终以 `read()` 返回 `-1` 为准。
