# Java 通配符使用注意点详解

Java 通配符（`?`）的核心价值在于**在泛型不可变的前提下，为方法参数提供受控的灵活性**。但这种灵活性是有代价的——编译器会对通配符施加严格的读写限制。理解这些限制背后的原因，比记住规则本身更重要。

---

## 先理解根源：泛型是不变的

Java 泛型默认不支持协变。即使 `Integer` 是 `Number` 的子类型，`List<Integer>` 也**不是** `List<Number>` 的子类型：

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers; // ❌ 编译错误
```

原因在于**写入安全**。假如允许这种赋值，就可以通过 `numbers` 向一个“实际上是 `List<Integer>`”的列表中添加 `Double`，随后从 `integers` 读取时就会发生 `ClassCastException`：

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers; // 假设允许
numbers.add(3.14);              // 把一个 Double 塞进了 List<Integer>
Integer i = integers.get(0);    // ClassCastException
```

通配符正是为了在不破坏写入安全的前提下，让方法参数能够接受“相关类型”的集合。

---

## 注意点一：用 PECS 原则选择 `extends` 还是 `super`

**PECS = Producer-Extends, Consumer-Super**。这是通配符使用中最重要的一条规则：

| 参数角色 | 行为 | 应使用的通配符 |
|---|---|---|
| **生产者**（Producer） | 从参数中**读取**数据 | `? extends T` |
| **消费者**（Consumer） | 向参数中**写入**数据 | `? super T` |
| 既是生产者又是消费者 | 既读又写 | **不用通配符**，用具体类型参数 `T` |

### 生产者：`? extends T`

```java
// 只读取，不写入 → 生产者，用 extends
public static double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) {   // ✅ 读取为 Number 是安全的
        total += n.doubleValue();
    }
    return total;
}

// 调用：List<Integer>、List<Double>、List<Long> 都可以传入
sum(Arrays.asList(1, 2, 3));
sum(Arrays.asList(1.1, 2.2));
```

如果写成 `List<Number>`，`List<Integer>` 将无法传入，方法就失去了通用性。`? extends Number` 解决了这个问题，同时保证了**读取时的类型安全**——无论实际列表元素是 `Integer` 还是 `Double`，都可以安全地当作 `Number` 来读取。

### 消费者：`? super T`

```java
// 只写入，不关心具体读取类型 → 消费者，用 super
public static void addAll(List<? super Integer> dest, int count) {
    for (int i = 0; i < count; i++) {
        dest.add(i);              // ✅ 写入 Integer 是安全的
    }
}

// 调用：List<Integer>、List<Number>、List<Object> 都可以作为目标
List<Number> numbers = new ArrayList<>();
addAll(numbers, 5);               // 向 List<Number> 中写入 Integer，合法
```

`? super Integer` 的含义是“目标列表的元素类型是 `Integer` 或它的某个父类型”，因此写入 `Integer` 及其子类一定是安全的。

**反例：不要用 `? extends T` 做消费者。**

```java
void addNumber(List<? extends Number> list) {
    list.add(42); // ❌ 编译错误
}
```

编译器无法确认这个列表的实际类型参数是 `Integer`、`Double` 还是其他 `Number` 子类，写入任何具体值都可能破坏类型安全，因此只允许写入 `null`。

---

## 注意点二：`extends` 只能读（`null` 除外），`super` 只能安全写

这是 PECS 原则的直接推论，但值得单独强调，因为它是通配符相关编译错误最常见的来源。

| 操作 | `List<? extends Number>` | `List<? super Integer>` |
|---|---|---|
| 读取 | ✅ 可读为 `Number` | ⚠️ 只能读为 `Object` |
| 写入 | ❌ 只能写 `null` | ✅ 可写 `Integer` 及其子类 |

```java
// extends：读安全，写几乎禁止
void readFrom(List<? extends Number> list) {
    Number n = list.get(0);  // ✅
    // list.add(1);          // ❌
    // list.add(3.14);       // ❌
    list.add(null);          // ✅ 唯一允许的写入
}

// super：写安全，读只能当 Object
void writeTo(List<? super Integer> list) {
    list.add(42);            // ✅
    list.add(Integer.valueOf(7)); // ✅
    Object obj = list.get(0);     // ✅ 但只能作为 Object
    // Integer i = list.get(0);   // ❌
}
```

`super` 的读取限制经常被忽视：虽然 `List<? super Integer>` 可能实际是 `List<Number>` 或 `List<Object>`，编译器只能保证元素“至少是 `Object`”，因此无法安全地向下转型为 `Integer`。

---

## 注意点三：通配符捕获——直接修改 `List<?>` 会失败

当你试图对 `List<?>` 或 `List<? extends T>` 执行**依赖于具体类型参数**的操作时，编译器会报 “capture of” 错误。典型例子是 `swap`：

```java
// ❌ 编译失败
public static void swap(List<?> list, int i, int j) {
    list.set(i, list.set(j, list.get(i)));
}
```

编译器将 `?` 捕获为一个**不可命名的类型**（通常显示为 `CAP#1`），`list.get(i)` 返回的是这个捕获类型，而 `list.set(j, ...)` 要求的也是同一个捕获类型。编译器无法确认两者是同一类型，因此拒绝编译。

**解决方案：用一个私有泛型辅助方法“捕获”通配符**：

```java
public static void swap(List<?> list, int i, int j) {
    swapHelper(list, i, j);        // 通配符在此处被捕获为具体类型 E
}

private static <E> void swapHelper(List<E> list, int i, int j) {
    list.set(i, list.set(j, list.get(i)));  // ✅ 类型一致，安全
}
```

当 `swapHelper(list, i, j)` 被调用时，编译器通过类型推断将 `List<?>` 中的 `?` 捕获为一个确定的类型变量 `E`，在辅助方法内部所有 `get`/`set` 都基于同一个 `E`，类型安全得到保证。`Collections.swap` 和 `Collections.reverse` 的内部实现都采用了这种模式。

## 注意点四：通配符的位置限制——不能定义泛型类，不宜作返回类型

### 不能用于定义泛型类/接口/方法

通配符只能出现在**使用**泛型类型的位置（方法参数、局部变量、字段类型），不能用来**声明**类型参数：

```java
class Box<?> { }                    // ❌ 语法错误
interface Foo<? extends Number> { } // ❌ 语法错误
<T> void method(List<T> list) { }   // ✅ 用类型参数 T 定义泛型方法
void method(List<?> list) { }       // ✅ 用通配符接受任意列表
```

定义泛型类型或泛型方法时，必须使用类型参数 `T`、`E` 等。

### 返回类型应避免使用通配符

用通配符作为返回类型，会把**类型问题转嫁给调用方**，迫使调用方也无法做具体类型操作：

```java
// ❌ 返回类型含通配符，调用方难以直接使用
public static List<? extends Number> mergeBad(List<Integer> a, List<Double> b) {
    List<Number> result = new ArrayList<>();
    result.addAll(a);
    result.addAll(b);
    return result;
}

List<Number> merged = mergeBad(a, b); // ❌ 编译失败，不能赋给 List<Number>
```

更好的做法是**参数用通配符（保持灵活性），返回值用类型参数（把精确类型还给调用方）**：

```java
public static <E> List<E> merge(
        List<? extends E> a, List<? extends E> b) {
    List<E> result = new ArrayList<>();
    result.addAll(a);
    result.addAll(b);
    return result;
}

List<Number> merged = merge(
    Arrays.asList(1, 2), Arrays.asList(1.1, 2.2)); // ✅ 返回 List<Number>
```

## 注意点五：通配符 vs 类型参数——什么时候该用哪个

类型参数 `T` 和通配符 `?` 不是可以随意互换的，选择依据是**类型是否需要在多个位置之间建立依赖关系**。

**规则：如果类型参数在方法声明中只出现一次，优先用通配符；如果出现在多个位置（参数之间或参数与返回值之间），必须用类型参数。**

```java
// 类型参数只出现一次 → 用通配符更简洁
public static void printAll(List<?> list) {        // ✅ 优于 <T> void printAll(List<T>)
    list.forEach(System.out::println);
}

// 类型参数出现在两个参数中，需要建立约束 → 必须用类型参数
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T item : src) {
        dest.add(item);   // T 同时约束了 src 的输出和 dest 的输入
    }
}
```

此外，两者在边界能力上有本质差异：

| 能力 | 类型参数 `<T>` | 通配符 `<?>` |
|---|---|---|
| 设置**上界** | ✅ `<T extends Number>` | ✅ `<? extends Number>` |
| 设置**下界** | ❌ 不支持 | ✅ `<? super Integer>` |
| **多重边界** | ✅ `<T extends A & B>` | ❌ 不支持 |

需要**下界**时只能用通配符（`? super T`）；需要**多重边界**时只能用类型参数（`T extends A & B`）。这是两者无法完全互相替代的根本原因。

---

## 补充：几个容易忽略的次要限制

**不能实例化通配符类型**。`new ArrayList<? extends Number>()` 是非法的；需要实例化时，必须指定具体类型。

**通配符类型并非完全不可读**。`List<? extends Number>` 的元素可以安全地当作 `Number` 读取；`List<?>` 的元素可以安全地当作 `Object` 读取。所谓“不能读”仅针对 `List<? super T>` 读取后**向下转型为 `T`** 的场景。

**避免使用裸类型（raw type）**。`List list` 会绕过所有泛型检查，与通配符 `List<?>` 有本质区别：前者是退化的非泛型类型，后者是类型安全的“任意类型列表”。

---

掌握通配符的关键不在于记住多少条规则，而在于理解一条主线：**通配符是为方法参数的灵活性服务的，它的读写限制是编译器保护类型安全的必然结果**。实际编码时，先判断参数是生产者还是消费者，再用 PECS 选择 `extends` 或 `super`，遇到“capture of”错误时用辅助方法捕获通配符，遇到返回类型时把通配符换成类型参数——这四步能覆盖绝大多数场景。
