# Java BufferedInputStream 详解

`BufferedInputStream` 是 Java I/O 中最常用、也最容易被“会用但说不清”的类之一。下面从它解决的问题出发，逐步拆解功能、构造器、核心 API，并用可运行的代码说明关键细节。

---

## 它解决的是什么问题

直接使用 `FileInputStream` 逐字节读取时，每调用一次 `read()` 都可能触发一次系统调用。对于小批量、高频的读取场景，这种“一次一个字节”的代价很高。

`BufferedInputStream` 的核心策略是：**在内部维护一个字节数组，一次性从底层流读入一批数据，后续的小量读取直接从内存缓冲区返回，直到缓冲区耗尽才再次“批量补货”**。OpenJDK 文档对此的描述是：它“adds functionality to another input stream—namely, the ability to buffer the input and to support the mark and reset methods”。

一句话概括：**用一次系统调用换多次内存访问，显著降低与底层流（文件、网络等）交互的频率**。

---

## 构造器

`BufferedInputStream` 有两个构造器，均接受一个底层 `InputStream`：

### 默认缓冲区大小

```java
public BufferedInputStream(InputStream in)
```

内部等价于 `this(in, 8192)`，默认缓冲区为 **8 KB**。

### 指定缓冲区大小

```java
public BufferedInputStream(InputStream in, int size)
```

`size` 必须大于 0，否则抛出 `IllegalArgumentException`。

```java
try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("data.bin"))) {
    // 使用默认 8KB 缓冲区
}

try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("data.bin"), 64 * 1024)) {
    // 使用 64KB 缓冲区
}
```

> 缓冲区大小并非越大越好：过大会增加单次 `fill()` 的内存拷贝开销和延迟敏感场景的首次读取等待时间。8 KB 对大多数中小文件足够；大文件或高吞吐场景可以适当调大（如 32 KB、64 KB）。

## 核心 API 与使用示例

### `read()` — 逐字节读取

从缓冲区取一个字节，返回 `0~255` 的 `int`；流末尾返回 `-1`。当缓冲区耗尽（`pos >= count`）时，内部调用 `fill()` 重新填充。

```java
try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("input.txt"))) {
    int b;
    while ((b = bis.read()) != -1) {
        System.out.print((char) b);
    }
}
```

**注意**：逐字节 `read()` 虽然已由缓冲加速，但仍不如**批量读取**高效。在性能敏感场景优先使用 `read(byte[])`。

---

### `read(byte[] b, int off, int len)` — 批量读取

将最多 `len` 个字节读入 `b`，从 `off` 开始存放，返回实际读取的字节数；末尾返回 `-1`。这是文件复制的标准写法：

```java
try (BufferedInputStream bis = new BufferedInputStream(
             new FileInputStream("source.bin"));
     BufferedOutputStream bos = new BufferedOutputStream(
             new FileOutputStream("dest.bin"))) {
    byte[] buf = new byte[8192];
    int n;
    while ((n = bis.read(buf)) != -1) {
        bos.write(buf, 0, n);
    }
}
```

**关键点**：最后一次读取时 `n` 可能小于 `buf.length`，所以写入必须用 `bos.write(buf, 0, n)`，而不是 `bos.write(buf)`。

---

### `mark(int readlimit)` / `reset()` — 标记与回退

这是 `BufferedInputStream` 相对于普通 `InputStream` 最核心的增强能力：**记住某个读取位置，之后可以回退到该位置重新读取**。

- `mark(readlimit)`：在当前 `pos` 处打标记，并设定“最大回退范围”`readlimit`。
- `reset()`：将 `pos` 重置到 `markpos`，后续读取从标记点重新开始。

`mark` 的语义需要特别注意：**`readlimit` 不是“最多可以回退的字节数”，而是“标记之后最多可以继续读多少字节而标记仍然有效”**。一旦 `pos - markpos` 超过 `marklimit`，标记即失效，此后调用 `reset()` 会抛出 `IOException`。

```java
try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("input.txt"))) {

    // 读取前 5 个字节
    byte[] head = new byte[5];
    bis.read(head);
    System.out.println("前5字节: " + new String(head));

    // 打标记，允许之后最多再读 100 字节而不失效
    bis.mark(100);

    // 继续读 10 字节
    byte[] mid = new byte[10];
    bis.read(mid);
    System.out.println("标记后10字节: " + new String(mid));

    // 回退到标记点
    bis.reset();

    // 重新读 10 字节——与上面完全相同
    byte[] midAgain = new byte[10];
    bis.read(midAgain);
    System.out.println("reset后重读: " + new String(midAgain));
}
```

**容易踩的坑**：如果 `mark(10)` 之后连续读取了 11 个字节才调用 `reset()`，标记已经因超出 `readlimit` 而失效，`reset()` 会抛出异常。`BufferedInputStream` **不会**因为 `readlimit` 小而自动扩容缓冲区来“保住”标记——它只是遵循 `InputStream` 的契约，超出范围就放弃标记。

---

### `skip(long n)` — 跳过字节

跳过最多 `n` 个字节，返回实际跳过的数量。`BufferedInputStream` 会**优先在缓冲区内部跳过**：如果缓冲区剩余数据足够，直接移动 `pos`，不触碰底层流；如果不够，且没有激活的标记，则委托底层流跳过；如果存在标记，则需要先 `fill()` 来保护标记之后的数据。

```java
try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("data.bin"))) {
    long skipped = bis.skip(1024);  // 跳过前 1024 字节
    int next = bis.read();           // 从第 1025 字节开始读
}
```

`skip` 的返回值可能小于请求值（例如底层流剩余字节不足），所以**不要假设一定跳过了 `n` 个字节**，应检查返回值或在循环中跳过。

---

### `available()` — 可无阻塞读取的字节数估计

返回“接下来可以在不阻塞的情况下读取或跳过的字节数估计”。`BufferedInputStream` 的实现是：**缓冲区剩余字节数（`count - pos`）+ 底层流的 `available()`**，并做了溢出保护。

```java
try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("data.bin"))) {
    int avail = bis.available();
    System.out.println("可无阻塞读取约: " + avail + " 字节");
    // 可以据此预分配数组，但不要依赖它判断流是否结束
}
```

**注意**：`available()` 返回的是**估计值**，不是“剩余总字节数”，也不是 EOF 的可靠判据。判断流结束始终应使用 `read() == -1`。

---

### `close()`

关闭流并释放底层资源。`BufferedInputStream` 关闭后会置空内部引用，后续读写操作抛出 `IOException`。务必使用 **try-with-resources**：

```java
try (BufferedInputStream bis = new BufferedInputStream(
        new FileInputStream("input.txt"))) {
    // 自动关闭，无需显式调用 close()
}
```

---

## 内部机制：这些 API 为什么这样工作

理解 `fill()` 的行为，就能理解 `mark/reset` 的边界条件。`fill()` 仅在缓冲区耗尽时触发，其逻辑根据**是否存在有效标记**分成两条路径：

- **无标记（`markpos == -1`）**：直接把 `pos` 归零，旧数据全部丢弃，从底层流重新填满缓冲区。
- **有标记且缓冲区已满**：不能丢弃 `markpos` 之后的数据。此时分三种情况：
  - `markpos > 0`：把 `[markpos, pos)` 的有效数据**整体前移**到缓冲区开头，腾出空间；
  - `markpos == 0` 且缓冲区大小已经 ≥ `marklimit`：**放弃标记**（`markpos = -1`），回到无标记模式；
  - 否则：**扩容缓冲区**，以容纳标记之后持续增长的数据。

这解释了为什么 `mark(readlimit)` 的 `readlimit` 是硬性边界：当缓冲区无法在不丢弃标记数据的前提下继续扩容或前移时，标记就被放弃。

## 性能对比：缓冲 vs 非缓冲

下面是一组实测数据（复制 150 MB 文件，使用 1 KB 读写数组）：

| 方式 | 耗时 |
|---|---:|
| `FileInputStream` / `FileOutputStream` 直接读写 | **2300 ms** |
| `BufferedInputStream` / `BufferedOutputStream` 包装后读写 | **623 ms** |

缓冲流在同一测试中约快 **3.7 倍**。差异主要来自系统调用次数的大幅减少：非缓冲方式即使使用 1 KB 数组，每次 `read` 仍可能触发底层 I/O；缓冲流则把多次小读合并为少量 8 KB 级别的底层读取。

## 使用要点速查

| 要点 | 说明 |
|---|---|
| 优先批量读取 | `read(byte[], off, len)` 优于逐字节 `read()` |
| `mark(readlimit)` 是“有效窗口” | 标记后读取超过 `readlimit` 字节，`reset()` 将失败 |
| `skip` 返回值要检查 | 实际跳过数可能小于请求值 |
| `available()` 仅作估计 | 不能用来判断 EOF，EOF 用 `read() == -1` |
| 始终用 try-with-resources | 确保 `close()` 被调用 |
| 缓冲区大小按场景调整 | 默认 8 KB；大文件/高吞吐可调大，延迟敏感场景不宜过大 |
