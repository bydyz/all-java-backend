# 单例模式详解

## 一、什么是单例模式

**单例模式（Singleton Pattern）** 是一种创建型设计模式，核心目标是：

> **保证一个类在系统运行期间只有一个实例，并提供一个全局访问点来获取这个实例。**

典型结构包含三要素：

1. **私有构造方法**：防止外部 `new` 创建对象；
2. **私有静态实例变量**：保存唯一实例；
3. **公有静态获取方法**：返回唯一实例。

---

## 二、单例模式的优点

1. **控制实例数量**：避免频繁创建销毁对象，节省内存和系统资源。
2. **全局统一访问**：例如全局配置、日志管理器，所有代码访问同一份数据。
3. **减少重复初始化开销**：如数据库连接池、线程池、缓存管理器。
4. **协调系统行为**：某些资源需要统一管理，例如设备管理器、ID 生成器。
5. **实现相对简单**：结构清晰，容易理解。

---

## 三、应用场景

适合“**系统中确实只需要一个实例，且需要全局访问**”的场景：

- 配置管理类：`AppConfig`
- 日志管理类：`LoggerManager`
- 数据库连接池、线程池
- 缓存管理器
- 全局 ID 生成器
- 设备管理器，如打印机后台服务
- Spring 容器中的默认 Bean 作用域（容器级单例）
- 工具类中的共享资源管理

注意：**不要为了全局访问而滥用单例**。单例会引入全局状态，增加耦合和测试难度。

---

## 四、实现思路

单例模式实现通常围绕以下问题：

1. **如何禁止外部创建对象？**

- 构造方法私有化。

2. **如何保存唯一实例？**

- 使用静态成员变量。

3. **如何提供全局访问？**

- 提供 `public static getInstance()` 方法。

4. **是否延迟加载？**

- 饿汉式：类加载时创建；
- 懒汉式：第一次使用时创建。

5. **如何保证线程安全？**

- 同步方法、双重检查锁、静态内部类、枚举等。

6. **如何防止反射、序列化、克隆破坏单例？**

- 枚举天然防反射和序列化破坏；
- 其他方式可在构造方法加检查，或实现 `readResolve()`。

---

## 五、常见实现方式及优缺点

| 实现方式      | 是否延迟加载 | 线程安全  | 优点              | 缺点                  |
|-----------|--------|-------|-----------------|---------------------|
| 饿汉式       | 否      | 是     | 简单，类加载机制保证安全    | 可能提前创建、浪费资源         |
| 懒汉式（非同步）  | 是      | 否     | 简单、延迟加载         | 多线程下可能创建多个实例        |
| 懒汉式（同步方法） | 是      | 是     | 简单安全            | 每次获取都加锁，性能较差        |
| 双重检查锁 DCL | 是      | 是     | 延迟加载且性能较好       | 实现较复杂，需要 `volatile` |
| 静态内部类     | 是      | 是     | 延迟加载、线程安全、代码简洁  | 反射/序列化仍需额外处理        |
| 枚举        | 否      | 是     | 最简洁、天然防反射和序列化破坏 | 不能延迟加载，扩展性有限        |
| 容器式/注册式   | 可控     | 需自行保证 | 可管理多个单例         | 实现复杂，需保证容器线程安全      |

---

# 六、代码详解（Java）

## 1. 饿汉式

```java
public class SingletonHungry {
    // 类加载时就创建唯一实例
    private static final SingletonHungry INSTANCE = new SingletonHungry();

    // 私有构造方法，防止外部 new
    private SingletonHungry() {
    }

    // 全局访问点
    public static SingletonHungry getInstance() {
        return INSTANCE;
    }

    public void doSomething() {
        System.out.println("饿汉式单例执行业务逻辑");
    }
}
```

### 特点

- 类加载时立即初始化实例。
- JVM 类加载机制保证线程安全。
- 不能延迟加载。
- 如果实例很大且不一定使用，可能浪费资源。

### 适用

实例较小、启动时一定需要、追求简单安全的场景。

---

## 2. 懒汉式：线程不安全

```java
public class SingletonLazyUnsafe {
    private static SingletonLazyUnsafe instance;

    private SingletonLazyUnsafe() {
    }

    public static SingletonLazyUnsafe getInstance() {
        if (instance == null) {
            // 多线程下可能多个线程同时进入，创建多个实例
            instance = new SingletonLazyUnsafe();
        }
        return instance;
    }
}
```

### 特点

- 第一次调用才创建，延迟加载。
- **线程不安全**。
- 多线程并发时可能创建多个实例。

### 适用

仅限单线程环境或学习演示，生产环境不推荐。

---

## 3. 懒汉式：同步方法

```java
public class SingletonLazySync {
    private static SingletonLazySync instance;

    private SingletonLazySync() {
    }

    // 对整个方法加锁，保证线程安全
    public static synchronized SingletonLazySync getInstance() {
        if (instance == null) {
            instance = new SingletonLazySync();
        }
        return instance;
    }
}
```

### 特点

- 延迟加载。
- 线程安全。
- 每次调用 `getInstance()` 都要获取类锁，性能较差。

### 适用

并发访问不高的场景。

---

## 4. 双重检查锁 DCL

```java
public class SingletonDCL {
    // volatile 禁止指令重排序，保证可见性
    private static volatile SingletonDCL instance;

    private SingletonDCL() {
    }

    public static SingletonDCL getInstance() {
        // 第一次检查：实例已创建则直接返回，避免加锁
        if (instance == null) {
            synchronized (SingletonDCL.class) {
                // 第二次检查：防止多个线程先后进入同步块重复创建
                if (instance == null) {
                    instance = new SingletonDCL();
                }
            }
        }
        return instance;
    }
}
```

### 为什么需要 `volatile`？

`instance = new SingletonDCL();` 可粗略分为：

1. 分配内存；
2. 初始化对象；
3. 将引用指向内存地址。

如果没有 `volatile`，可能发生指令重排序：引用先指向未初始化完成的对象。其他线程可能拿到一个“非 null
但未初始化完成”的对象。`volatile` 禁止相关重排序并保证可见性。

### 特点

- 延迟加载。
- 线程安全。
- 第一次创建时加锁，后续读取不加锁，性能较好。
- 实现较复杂。

### 适用

需要延迟加载且并发较高的场景。

---

## 5. 静态内部类

```java
public class SingletonHolder {
    private SingletonHolder() {
    }

    // 静态内部类在第一次被访问时才会加载
    private static class Holder {
        private static final SingletonHolder INSTANCE = new SingletonHolder();
    }

    public static SingletonHolder getInstance() {
        return Holder.INSTANCE;
    }
}
```

### 特点

- 外部类加载时不会立即初始化内部类，因此实现延迟加载。
- JVM 保证类初始化线程安全。
- 代码简洁，性能好。
- 反射和序列化仍可能破坏单例，需要额外防护。

### 适用

Java 中常用的推荐实现之一。

---

## 6. 枚举单例

```java
public enum SingletonEnum {
    INSTANCE;

    public void doSomething() {
        System.out.println("枚举单例执行业务逻辑");
    }
}
```

使用：

```java
SingletonEnum.INSTANCE.doSomething();
```

### 特点

- 写法极简。
- JVM 保证线程安全。
- **天然防止反射破坏**：反射创建枚举对象会抛异常。
- **天然防止序列化破坏**：枚举序列化不会创建新实例。
- 不能延迟加载。
- 枚举不能继承其他类，扩展性有限。

### 适用

绝大多数不需要延迟加载的单例场景，《Effective Java》推荐方式。

---

## 7. 容器式/注册式单例（扩展）

```java
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class SingletonRegistry {
    private static final Map<String, Object> INSTANCE_MAP = new ConcurrentHashMap<>();

    private SingletonRegistry() {
    }

    public static void register(String key, Object instance) {
        INSTANCE_MAP.putIfAbsent(key, instance);
    }

    @SuppressWarnings("unchecked")
    public static <T> T getInstance(String key) {
        return (T) INSTANCE_MAP.get(key);
    }
}
```

### 特点

- 一个容器管理多个单例。
- 适合框架级管理，如 Spring 的 Bean 容器。
- 需要自行控制线程安全和注册时机。

---

## 七、如何防止单例被破坏

### 1. 反射破坏

非枚举单例可通过反射调用私有构造方法创建新对象。可在构造方法中加判断：

```java
private SingletonDCL() {
    if (instance != null) {
        throw new RuntimeException("单例已被创建，禁止反射创建");
    }
}
```

但更推荐枚举方式。

### 2. 序列化破坏

实现 `readResolve()`：

```java
private Object readResolve() {
    return getInstance();
}
```

### 3. 克隆破坏

避免实现 `Cloneable`，或重写 `clone()` 抛异常。

---

## 八、总结与选择建议

- **追求最简单、最安全**：枚举单例；
- **需要延迟加载且代码简洁**：静态内部类；
- **需要延迟加载且可接受复杂实现**：双重检查锁；
- **实例小且启动必用**：饿汉式；
- **生产环境避免**：非同步懒汉式；
- **并发很低且实现简单**：同步方法懒汉式。

最后强调：**单例保证的是“实例唯一”，不保证实例内部状态线程安全**。如果单例对象包含可变状态，仍需使用同步、锁或并发容器保证线程安全。
