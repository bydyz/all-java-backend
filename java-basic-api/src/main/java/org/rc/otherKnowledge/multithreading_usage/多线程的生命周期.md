JDK 1.5 是 Java 多线程生命周期模型的一个关键分界点。在此之前，生命周期的描述更贴近操作系统的调度视角，状态划分相对粗略；JDK 1.5 引入 `java.util.concurrent` 包后，不仅将**线程个体的状态**标准化为明确的枚举，还引入了**线程池自身的生命周期**这一全新维度。下面分这两个层面来说明。

---

### JDK 1.5 之前：操作系统视角的“五状态”模型

在 JDK 1.5 之前，Java 对线程生命周期的描述通常沿用操作系统层面的 **五状态模型**：新建、就绪、运行、阻塞、死亡。

**新建**：通过 `new Thread(...)` 创建了 `Thread` 对象，但尚未调用 `start()`。此时线程仅在 JVM 中分配了内存，还没有与真正的操作系统线程关联。

**就绪**：调用了 `start()` 方法后，线程进入就绪状态。它已经具备了运行条件，但需要等待 JVM 的线程调度器分配 CPU 时间片。

**运行**：就绪状态的线程获得了 CPU，开始执行 `run()` 方法中的代码。

**阻塞**：运行中的线程因为某些原因放弃 CPU，暂时停止执行。进入阻塞的典型原因包括：调用 `sleep()`、等待 I/O 完成、试图获取被其他线程持有的 `synchronized` 锁、调用 `wait()` 等待通知、被 `suspend()` 挂起（已过时）等。**在五状态模型中，“阻塞”是一个笼统的概念**，上述所有导致线程暂停执行的情况都被归入其中。当阻塞原因解除后，线程回到就绪状态，重新等待 CPU 调度。

**死亡**：`run()` 方法正常执行完毕，或抛出了未捕获的异常/错误，线程结束生命周期。

这个模型的问题在于，“阻塞”含义过于宽泛，无法区分“等待锁”、“等待通知”、“限时睡眠”等本质不同的等待行为。JDK 1.5 的标准化正是为了解决这个问题。

---

### JDK 1.5 及之后：标准化为 `Thread.State` 六种状态

JDK 1.5 在 `java.lang.Thread` 内部定义了 `public enum State`，将线程状态精确划分为六种：

```java
public enum State {
    NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED
}
```

**`NEW`**：对应之前的“新建”，线程对象已创建但尚未 `start()`。

**`RUNNABLE`**：对应之前的“就绪”与“运行”的合并。JVM 不区分线程是在等待 CPU 时间片还是正在 CPU 上执行，两者统一为 `RUNNABLE`。Javadoc 明确指出，处于 `RUNNABLE` 的线程正在 JVM 中执行，但它可能仍在等待操作系统的其他资源（如处理器）。

**`BLOCKED`**：含义被**收窄**了。它特指线程正在**等待获取监视器锁**以进入 `synchronized` 块或方法，或者在调用 `Object.wait()` 后等待重新进入同步块。

**`WAITING`**：线程在**无限期地等待**另一个线程执行特定动作。触发方法包括无超时的 `Object.wait()`、无超时的 `Thread.join()` 以及 `LockSupport.park()`。

**`TIMED_WAITING`**：线程在**有限时间内等待**。触发方法包括 `Thread.sleep(long)`、带超时的 `Object.wait(long)`、带超时的 `Thread.join(long)` 以及 `LockSupport.parkNanos/parkUntil`。

**`TERMINATED`**：线程已退出 `run()` 方法，生命周期结束。

这一标准化的核心价值在于：`BLOCKED`、`WAITING`、`TIMED_WAITING` 三者被区分开来，分别对应**等待锁**、**无限期等待信号**和**有限期等待**三种不同性质的暂停。这为监控和诊断提供了更精确的语义。

#### 代码示例：通过 `getState()` 观察状态转换

下面的代码片段通过 `Thread.getState()` 观察一个线程从 `NEW` → `RUNNABLE` → `TIMED_WAITING` → `TERMINATED` 的过程。

```java
Thread t = new Thread(() -> {
    try {
        Thread.sleep(2000); // 进入 TIMED_WAITING
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});

System.out.println(t.getState()); // NEW
t.start();
Thread.sleep(100); // 让 t 有机会开始执行
System.out.println(t.getState()); // TIMED_WAITING（或短暂 RUNNABLE 后进入 TIMED_WAITING）
t.join();
System.out.println(t.getState()); // TERMINATED
```

对于 `BLOCKED` 和 `WAITING`，可以通过竞争同一个锁以及 `wait/notify` 来分别构造，但需要注意状态转换的时序性，`getState()` 反映的是调用瞬间的“快照”。

### JDK 1.5 引入的新维度：`ThreadPoolExecutor` 自身的生命周期

JDK 1.5 在引入 `ThreadPoolExecutor` 的同时，也为**线程池本身**定义了独立于线程个体的生命周期状态。线程池是一个“容器”，它的生命周期管理的是**接受任务、执行任务、关闭和清理**的宏观过程，与池内单个工作线程的状态是不同层面的概念。

`ThreadPoolExecutor` 内部用 `runState` 表示线程池状态，共五种：

| 状态 | 含义 |
|---|---|
| **`RUNNING`** | 正在运行，接受新任务并处理排队任务 |
| **`SHUTDOWN`** | 准备关闭，不接受新任务，但会继续处理队列中已有的任务 |
| **`STOP`** | 停止，不接受新任务，不处理排队任务，并中断正在执行的任务 |
| **`TIDYING`** | 整理，所有任务已终止、工作线程数为 0，将运行 `terminated()` 钩子方法 |
| **`TERMINATED`** | 终止，`terminated()` 已完成 |

状态之间的核心转换路径包括：

- **`RUNNING` → `SHUTDOWN`**：调用 `shutdown()`；
- **`RUNNING` / `SHUTDOWN` → `STOP`**：调用 `shutdownNow()`；
- **`SHUTDOWN` / `STOP` → `TIDYING`**：等待所有任务结束、工作线程归零；
- **`TIDYING` → `TERMINATED`**：`terminated()` 钩子执行完毕。

#### 代码示例：线程池状态转换

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    2, 4, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(10)
);

System.out.println(pool.isShutdown()); // false（RUNNING）

pool.execute(() -> {
    try { Thread.sleep(500); } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});

pool.shutdown();                        // RUNNING → SHUTDOWN
System.out.println(pool.isShutdown());  // true
System.out.println(pool.isTerminated());// false（队列中可能还有任务）

pool.awaitTermination(2, TimeUnit.SECONDS);
System.out.println(pool.isTerminated());// true（已进入 TERMINATED）
```

若在此过程中调用 `shutdownNow()`，状态会从 `SHUTDOWN`（或 `RUNNING`）直接跃迁到 `STOP`，执行中的任务会被中断，未执行的任务从队列中取出并返回。

---

### 两者的关系与区分要点

**`Thread.State` 管理的是“一个执行流当前在做什么”**：它是 NEW、是在跑、是在等锁、是在等信号、还是已经结束。`getState()` 返回的是某一瞬间的快照。

**`ThreadPoolExecutor` 的 `runState` 管理的是“这个线程池容器当前处于什么运营阶段”**：它是否还接收新任务、是否还要消化积压任务、是否正在中断执行中的任务、是否已经彻底清理完毕。二者不在同一个抽象层次上，但在实际运行中相互关联——例如线程池进入 `SHUTDOWN` 后，池内已有的工作线程可能仍在 `RUNNABLE` 状态继续执行队列中剩余的任务；线程池进入 `TERMINATED` 后，池内的工作线程均已退出（各自的 `Thread.State` 为 `TERMINATED`）。理解生命周期时，将“线程个体的状态”与“线程池的状态”分开看待，可以避免把两个不同维度的概念混为一谈。
