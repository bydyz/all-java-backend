# Swagger UI 能否按 Controller 中接口的定义顺序排序？

很遗憾，**不能直接、自动地**让 Swagger UI 严格按照 Controller 中 Java 方法的**书写顺序**来排序。你看到的“默认顺序”通常并不可靠，但这不代表无法实现类似的效果，只是需要**显式地告诉它顺序是什么**。

---

## 一、为什么“默认顺序”不是你写的顺序？

Springdoc 生成的 OpenAPI 文档（`/v3/api-docs`）中，接口路径被存储在一个 `LinkedHashMap` 里，这个结构本身**是会保留插入顺序的**。问题在于，这个“插入顺序”并不是来自你源码里的书写顺序。

Java 反射机制在获取一个类的方法时，**并不保证**返回的顺序和源码一致。这个顺序会受到 JVM 实现、类加载器行为、甚至编译优化等多种因素的影响。Springdoc 作为“服务器端”，返回给 Swagger UI 的就是这个由反射决定的、不稳定的顺序。Springdoc 官方也确认，“端点顺序与它们在类中定义的顺序并不一致”。

---

## 二、如何实现“类似定义顺序”的效果？

既然无法自动获取，就需要手动赋予顺序。以下是几种从简单到复杂的方案。

### 方案一：手动标注 `@Operation(order = n)`（最推荐）

这是最直接、最可控的方法。你可以在每个接口方法上，用 `@Operation` 注解的 `order` 属性来指定一个整数值，**值越小，排序越靠前**。

```java
@Operation(summary = "创建用户", order = 1)
@PostMapping
public User create(...) { ... }

@Operation(summary = "查询用户列表", order = 2)
@GetMapping
public List<User> list(...) { ... }
```

同时，必须在 `application.yml` 中启用按 `order` 属性排序：

```yaml
springdoc:
  swagger-ui:
    operations-sorter: order
```

这种方法让你能完全按照业务逻辑（如“创建 -> 查询 -> 更新”）来编排顺序，而不是依赖不可靠的源码顺序。

---

### 方案二：使用 `OperationCustomizer` 半自动排序

当接口数量很多时，逐个添加注解会很繁琐。你可以编写一个 `OperationCustomizer`，根据某种规则（比如方法名、自定义注解）自动为接口分配 `order` 值。

例如，可以自定义一个 `@ApiOrder` 注解，然后用 `OperationCustomizer` 读取这个注解的值并设置到 `operation` 对象上。这相当于把你手动指定的顺序，通过代码自动完成了。

---

### 方案三：理解 `springdoc.writer-with-order-by-keys=true` 的作用

这个配置项经常被提及，但它**并不能**实现“源码定义顺序”。它的作用是让输出的 OpenAPI 文档具有**确定性的、可预测的顺序**（通常是按字母顺序），以便于版本对比和调试。它解决的“混乱”问题，而非“按源码顺序”排列的问题。

---

### 方案四：基于字节码解析的“终极”方案（不推荐）

理论上是存在一种完全自动化的方法：通过读取编译后的 `.class` 文件，解析其中的 `LineNumberTable` 属性，来获取方法在源码中的真实行号，然后按行号排序。

但这需要引入 ASM 等字节码操作库，实现复杂度极高，且可能因编译器版本或调试信息的有无而失效，**在生产项目中极其罕见，不建议采用**。

---

## 三、总结

**无法直接实现“按源码顺序自动排序”**。Swagger UI 的默认顺序受 Java 反射机制影响，是不可控的。

要实现符合你预期的顺序，最务实的方法是**放弃对“自动”的期待，转而使用 `@Operation(order = n)` 手动指定**。这虽然需要一些额外的工作，但换来的是完全可控、稳定且符合业务逻辑的文档展示顺序，是实践中公认的最佳方案。
